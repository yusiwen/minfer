## 1. Background — the syncs and the staged bytes scale with the block count

Record [118](./118-c4-fa-prefill-double-buffer.md) shipped the double buffer only at hd 64: at hd 128 a
second tile pair took the block from 34,816 to 52,224 B, which on this device's 102,400 B per SM cut
the resident blocks from 2 to 1 and measured **+14.6%**. The arithmetic that mattered there was
"per-block bytes decide the block count" — and the block count is also what the *fixed* costs scale
with: one `__syncthreads()` per 32-key tile per block, and one staged copy of the window per block.
Halving the number of blocks halves both.

A block could hold more query rows only if its warps each still owned a 16-row fragment block (the
FAP2 decomposition), so 128 rows means 8 warps. Two things blocked that:

1. **The tail store staged the output tile through shared memory** — `FA_TQ * hd` f32, i.e. 64 KB at
   hd 128 with the wider tile, more than the block's entire budget.
2. **Register pressure** could have halved the resident warps.

Both turned out to be answerable: the tail store becomes a predicated per-element store (each lane
already knows its two fragment rows and its column pair from the softmax), and `ptxas` reports the
same 127-132 registers per thread at 256 threads, i.e. 33.5 K of the 65,536 register file — **one
block either way**. That is the key: at 256 threads the block count is *register-bound* at one, so the
doubled Q tile **and** the doubled K/V pair are free in shared-memory terms.

## 2. Principle — what the block count buys

Per prompt the k-loop work is the same; what changes is how often the fixed per-block costs are paid:

| | 64-row tile (before) | 128-row tile (after) |
|---|---|---|
| blocks per (layer, head) at `pp2048` | 32 | **16** |
| resident blocks/SM at hd 128 (f16, double-buffered) | 2 × 4 warps = 8 warps | **1 × 8 warps** |
| `__syncthreads()` per layer | 32 tiles × 64 k-steps = 2 048 | **1 024** |
| staged K/V bytes per layer | 32 × window | **16 × window** |
| block smem at hd 128 (f16) | 34,816 B | **69,632 B** (over the 48 KiB default → opt-in) |

Warps per SM are unchanged (8); the sync count and the staged bytes halve. The measured −7.9% is that
difference, and the hd-64 cell reading flat says the effect is about the *hd-128* block occupancy
regime, not a general win.

## 3. Implementation

- `FA_TQ 64 → 128`, `FA_NT = 2 * FA_TQ` (256 threads); every hard-coded `128` in the q load, the
  staging calls and the store loops becomes `FA_NT`; `warp = tid >> 5` now spans 0..7 and `wm * 16`
  covers the 128 rows.
- **The tail store** no longer stages through shared memory: each lane writes its two fragment rows
  with a `t < nt` predicate (`r0 = lane >> 2`, `r1 = r0 + 8`, column pair `2 * (lane & 3)` and its +8
  partner per 16-column block) — the same mapping the rescale and the `pa` packing already use. The
  full-tile path keeps `wmma::store_matrix_sync`.
- **The smem opt-in is back for hd 128** (every instantiation is now above the 48 KiB default:
  52,224 B packed, 69,632 B f16), via `fa_optin_hd128()` — eager in `minfer_prewarm_attention_prefill_kernels`
  (ADR-0034) and lazily re-checked in the launcher with a cached flag, so a capture window never makes
  the driver call. hd 64 stays under the cap (27,648 / 36,864 B) and needs none.
- **The double buffer no longer needs a head-dim gate**: `NBUF = (LAYOUT == KV_LAYOUT_F16) ? 2 : 1`.
  At 256 threads the block count is one either way, so the pair that cost 14.6% at 64 rows is free at
  128 — and the hd-128 f16 launch gets both changes at once.
- The Rust mirror of the tile width (`src/cuda/methods/attention.rs`'s `FA_TQ`, which gates the
  once-per-layer staging plane on `nt > FA_TQ`) moves to 128 with the kernel.
- The packed parity gate's shape moves from `nt = 100` to **`nt = 200`** (two tiles: one full, one
  tail) because a 100-token prompt no longer exceeds one tile — and that shape now exercises both
  output-store paths.

## 4. Verification

- `scripts/cuda_test.sh`: **868 passed / 0 failed / 62 ignored** (unchanged count).
- **Bit identity across the tile width**: the same prompt (`"The capital of France is"`, 4 tokens,
  f16 cache, 0.5B) run through the previous binary and this one with `MINFER_GRAPH_DUMP` produces
  **119 of 119 files identical** — the prefill and decode logits and the layer-0 K/V. This is the
  expected result (each query row's softmax reduces over k in the same order; the tile only decides
  which rows share a block) and it is what was measured, not assumed.
- Parity: the CPU-reference deltas are unchanged (3.44e-4 / 2.78e-4 f16, 6.72e-4 / 4.80e-4 packed at
  hd 64/128) and the packed gate's `MINFER_NO_KV_STAGE=1` arm still requires 0 differing elements.
- `ptxas`: 0 spill bytes; 80-86 registers for the packed instantiations, 128-132 for the f16 ones.
- nsys medians per launch (f16 cache, `pp2048`, earlier binary vs this one): hd 128 **416.3 →
  383.4 µs**, hd 64 **166.4 → 167.7 µs**; packed hd 128 **413.8 → 382.5 µs**, pass unchanged
  (37.2 → 36.3 µs).
- `pp8192` (f16, hd 128, `-n 32 --n-ctx 16384`, 3 alternating rounds): **7 463.7 → 7 696.8 tok/s
  (1.0312x)**. `pp2048` reads inside the +-2% session band, which is the honest reason the 8k shape
  is quoted for the prompt-level claim.

## 6. Lessons

1. **The block count is a lever, not just a consequence.** The same tile pair that cost 14.6% at 64
   rows is free at 128, because the wider block moves the binding constraint from shared memory to
   registers. Price a shape change by *which* resource it changes the constraint on.
2. **A tail path can be a shape blocker.** The 64 KB f32 staging existed because a 64-row tail was
   cheap to stage; the predicated per-element store removed the dependency and made the wider tile
   possible. The old path was not wrong, it was just carrying a constraint nobody had priced.
3. **Bit identity is testable across a shape change.** Two binaries, one prompt, `MINFER_GRAPH_DUMP`,
   119 files compared — a stronger claim than any tolerance, and cheap. The parity gates then keep
   pinning the *numerics* while this pins the *equivalence*.
