# 0058. A request's tools reach the prompt as the client wrote them, and a template that drops them refuses by name

- Status: Accepted
- Date: 2026-10-19
- Issues: #597
- Amends: ADR-0019 (its refusal contract now covers a request field, not only a template construct)

## Context

ADR-0019 fixed what happens when a template *cannot* render: a loud refusal naming the
construct, never a silent generic prompt. It said nothing about a template that renders
**successfully but incompletely**, because until now no request could make that happen.

The render path pinned `tools` to `none` — transformers' default — and the server's
request body had no `tools` field at all. So the Qwen2.5 template's `{% if tools %}`
branch had never executed inside this engine, and three things nobody had measured hid
behind it:

- **`tojson` did not exist.** minijinja is built here with `default-features = false`
  and `features = ["builtins", "serde"]`; the `tojson` filter is gated on the separate
  `json` feature. Every template whose tools branch echoes a tool would have failed at
  the missing filter.
- **minijinja's builtin `tojson` is the wrong reference anyway.** It is compact
  (`serde_json::to_string`) and HTML-escapes `<`, `>`, `&`, `'`. transformers overrides
  Jinja2's filter with plain `json.dumps(..., ensure_ascii=False)`, which separates with
  `", "`/`": "` and escapes none of those. Either difference alone changes the prompt.
- **Both JSON layers sort object keys.** `serde_json`'s `Map` and minijinja's `ValueMap`
  are `BTreeMap`s, so an OpenAI tool definition
  (`{"type": …, "function": …}`) would reach the model as
  `{"function": …, "type": …}` — a prompt no other implementation produces, and one the
  committed reference cannot match.

## Decision

**1. `tools` is carried, not modelled.** The request's array is deserialized into
`template::ToolJson`, an order-preserving JSON value, and handed to the template
verbatim. A typed `Tool` struct was rejected because `| tojson` echoes whatever it is
given: dropping an unknown key (OpenAI's `strict`, a vendor extension) or re-spelling a
number would change the prompt behind the client's back.

**2. `tojson` is CPython's `json.dumps`.** The engine registers its own filter:
separators `", "`/`": "`, `ensure_ascii=False`, no HTML escaping, `indent` honoured,
and any other keyword (`sort_keys`, `separators`, `ensure_ascii`) **refused by name**
rather than silently ignored. The authority is a committed CPython fixture
(`tests/fixtures/chat/tojson_cpython.json`, generated by `scripts/gen_chat_fixtures.py
--check`), not a hand-written expectation.

**3. Key order is a render-path property only.** `minijinja`'s `preserve_order` feature
is enabled, because its `ValueMap` is otherwise a `BTreeMap` and would re-sort what the
deserializer just preserved. `serde_json`'s matching feature is deliberately **not**
enabled: it is process-wide, and the JSON-Schema→GBNF compiler iterates a schema's map,
so the generated grammar — and the language it accepts — moves with the flag. That was
measured, not assumed: enabling it turned four grammar gates red, one of them on a legal
JSON object (`{"next":…,"v":1}`) that the compiler's fixed property chain then rejected.

**4. A template that does not put the tools into the prompt refuses by name.** The check
is mechanical: the same conversation is rendered twice at **one fixed instant** (one
`CivilTime` for both passes, so a `strftime_now` template cannot look tools-sensitive),
and byte-identical output means the definitions reached nothing. The refusal is
`TemplateError { kind: "tools not rendered" }`, which the server returns as a `400`; the
message says whether a model template lacks a branch or the GGUF fell back to ChatML.
Inspecting the template text was rejected: a branch can be guarded on a value this
engine does not pass, or render an empty block, and only the output can tell us which.

**5. `tool_choice` is honoured where a prompt can express it.** Absent or `"auto"`
renders the tools; `"none"` renders *without* them, because no output extraction exists,
so a prompt that still showed the schemas would invite a call the server would return as
ordinary content; `"required"` and a forced `{"type":"function",…}` are `400`s that name
the missing piece. Accepting a field and ignoring it is the silent substitution
ADR-0019 forbids, applied to a request instead of a template.

**6. Tool-call extraction is out of scope.** Parsing the model's `<tool_call>` output
into `choices[].message.tool_calls` is a separate increment (a streaming, partial-JSON
problem of its own); this decision covers the prompt side only, and the ticket says so.

## Alternatives considered

- **`serde_json`'s `preserve_order` only** (no `ToolJson`, no minijinja feature).
  Rejected: it is global, and it moves the grammar feature's accepted language. A
  render-only decision must not steer a sampler-side option.
- **Echo the raw request text for `| tojson`.** Rejected: a template may index into the
  tools (`tools[0].function.name`), which raw text cannot serve, and `tojson` is defined
  on a parsed value.
- **Ship the `json` feature and use minijinja's builtin `tojson`.** Rejected on measured
  bytes: compact separators and `\u003c` escaping both diverge from transformers
  (mutation-checked — reverting to the compact serializer fails three gates).
- **Silently render the tools-free prompt when the template has no branch.** Rejected:
  the client asked for tool definitions and would get a 200 without them; acceptance says
  "refused by name … never silently dropped".
- **Accept `tool_choice: "required"` and hope.** Rejected: the call would come back as
  content with no `tool_calls`, which is indistinguishable from the model refusing.
- **A typed `ToolDefinition` struct.** Rejected: see decision 1.

## Consequences

- A request carrying `tools` for a model whose template has a tools branch renders
  transformers' bytes; four committed reference cases gate it (one tool, two nested
  schemas with `<`/`&`/non-ASCII and a fractional default, no system message, and a
  replayed tool response), and all 28 existing tools-free cases stay byte-identical.
- `template::ToolJson` exists **only** for the render path; every other JSON surface
  keeps `serde_json`'s sorted map, so the grammar compiler is untouched.
- `tool_choice` is partially implemented by design (no `required`, no forced function):
  both are documented `400`s, and enabling them is the extraction increment.
- Known limits, recorded rather than hidden: a tool value is re-emitted by `serde_json`
  (so an exponent-form float may spell `1e30` where CPython writes `1e+30`); a message
  object is still built from `(role, content)` — the request's `tool_calls` on an
  assistant turn, and the client's key order *inside* a message, are not carried
  ([#613](https://github.com/yusiwen/minfer/issues/613)); and nothing parses the
  model's `<tool_call>` output back into `tool_calls`
  ([#614](https://github.com/yusiwen/minfer/issues/614)).
- The engine's dependency graph gains `minijinja`'s `preserve_order` feature (and
  `indexmap` with it) — one feature on an existing dependency, no new direct crate.
