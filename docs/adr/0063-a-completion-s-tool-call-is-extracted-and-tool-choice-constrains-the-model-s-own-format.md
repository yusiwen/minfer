# 0063. A completion's tool call is extracted, and `tool_choice` is a grammar on the model's own call format

- Status: Accepted
- Date: 2026-10-30
- Issues: #614
- Amends: ADR-0019 (a generation that ends inside a call is a named refusal, not content)
- Completes: ADR-0062 decision 6 (the response side reuses the carrier's shape)

## Context

ADR-0062 made the request side carry `tool_calls`; nothing parsed what the model
*writes*. A `<tool_call>{"name": …, "arguments": …}</tool_call>` block came back as
ordinary `choices[].message.content` with `finish_reason: "stop"`, which is why
`tool_choice: "required"` and a forced function were `400`s naming the missing
extraction (`src/server/types.rs::prompt_tools`): accepting them would have
promised a call the server could not report.

Two references shaped the answer. transformers 5.17.0 ships
`transformers.utils.chat_parsing.parse_response` with a Qwen2/Qwen3 response
template, so the expected `tool_calls` can be generated by another implementation
— the same rule ADR-0058 set for rendering. llama.cpp reaches `tool_choice` by
building a grammar from the template's own call syntax; minfer has no template
analysis, but it does have a GBNF compiler and a JSON-object prelude.

## Decision

**1. Extraction lives at the HTTP layer.** Both engines (serial and batched) already
report text through `StreamEvent`, so the parser runs where the response is built
(`src/server/mod.rs`), not inside a generation loop — one seam, two engines, no
new event variants.

**2. The parser is incremental and span-aware.** `src/server/toolcall.rs` holds back
a suffix that could still become `<tool_call>` (the tag can split across chunks),
parses the block only once its JSON value is complete, and never finds the closing
tag with `str::find`: the arguments may contain `</tool_call>` inside a string. A
complete JSON value with no closing tag at EOS is a usable call (transformers
closes the region implicitly); arguments cut off are an error.

**3. The arguments are the model's bytes.** A JSON object (array, number, …) is
carried as its own source slice — whitespace and key order included — through
`serde_json`'s `raw_value`; a JSON *string* is decoded, because OpenAI sends the
call's arguments as text. Schema validation of the arguments is the client's job.

**4. A response carries OpenAI's shape.** `message.tool_calls` (id, `type:
"function"`, name, arguments), `finish_reason: "tool_calls"`, `content` = the text
outside blocks. The model writes no id, so one `call_…` id is synthesised per call —
a client needs it for the follow-up `tool` message's `tool_call_id` (llama.cpp
leaves it out; OpenAI's shape requires it).

**5. Streaming reuses the non-streaming mapping.** A call becomes a
`delta.tool_calls` start chunk (index, id, name) plus one arguments fragment, and
the finish chunk reports `tool_calls`; content keeps streaming as content. The
event→chunk function is shared by the handler and its differential test, so
"concatenating the deltas reproduces the non-streaming call" is asserted against
the shipped code. Arguments are emitted as one fragment on purpose: a partial JSON
string cannot be un-escaped without a second state machine, and the model's bytes
must arrive whole.

**6. A truncated call is a named refusal.** Non-streaming: `400
invalid_request_error` naming the block. Streaming: the error frame instead of the
finish chunk. Never a `200` with half a call in `content`.

**7. `tool_choice` is enforced by a grammar on the model's own format.**
`"required"` enumerates the offered tool names; a forced function fixes one. The
wrapper (`<tool_call>`, the `{"name": …, "arguments": …}` object, `</tool_call>`) is
literal, and the arguments reuse the schema compiler's `j-object` language
(`grammar::GENERIC_RULES`, now `pub(crate)`), so extraction and the constraint agree
by construction. Boundaries are named `400`s: a template without the `<tool_call>`
format (other families need template analysis, the work llama.cpp's auto-parser
does), a combination with `grammar`/non-text `response_format` (two constraints),
the speculative draft engine (a grammar), and a forced name that is not offered.

**8. Parsing does not depend on `tools` having been sent.** A completed block is a
call; returning it as content would be the silent drop ADR-0019 forbids.

## Alternatives considered

- **Buffer the whole completion and parse at the end.** Rejected: content would stop
  streaming and the opening tag's holdback is the only place an incremental parser
  is actually needed.
- **Stream arguments as they arrive.** Rejected for now: it needs an escaping-aware
  JSON string state machine, and the acceptance is concatenation equality. Recorded
  as a limit, not a hidden one.
- **Split the block with `str::find("</tool_call>")`.** Rejected on a witness: the
  arguments may contain that literal, and the reference parser *does* mis-split
  there (recorded as the fixture's one divergence).
- **Re-encode the arguments with `serde_json`.** Rejected: it would re-spell the
  model's bytes (spacing, escapes), and the point of the extraction is fidelity.
- **Leave `tool_calls[].id` empty like llama.cpp.** Rejected: a replay needs an id
  the client can echo as `tool_call_id`.
- **Accept `tool_choice` without constraining.** Rejected: that is the silent
  substitution ADR-0019 forbids; a `200` with prose would look like the model
  refused.
- **Constrain every template family.** Rejected as scope: it needs the template
  analysis llama.cpp's auto-parser performs. Other families stay a named `400`.
- **Validate the arguments against the tool's JSON schema.** Rejected as scope: the
  server carries the call; schema validation belongs to the caller (and the
  reference parser's casts would not survive as bytes).

## Consequences

- A completion containing a call now returns `finish_reason: "tool_calls"` and
  `message.tool_calls`; a client that ignored the field sees the same prompt-side
  behaviour and a different content field (the block is no longer in it).
- A generation cut off inside a block is a `400` (non-streaming) or an error frame
  (streaming) instead of a `200` with partial JSON in `content`.
- `tool_choice: "required"`/forced work on the `<tool_call>` format; other formats
  answer a `400` naming the reason, tracked as a follow-up.
- `serde_json` gains its `raw_value` feature. It is behaviour-neutral: unlike
  `preserve_order` (ADR-0058), it adds a span-carrying type and changes no map
  ordering or grammar.
- The reference is transformers' parser, not this engine: 12 committed cases, one
  recorded divergence (the closing-tag-in-a-string case, where this parser is
  stricter about JSON and more correct about regions).
- Known limits: arguments are one streamed fragment; only the `<tool_call>` family
  is constrained; `content` is `""` when a call is the whole message (llama.cpp's
  convention).
